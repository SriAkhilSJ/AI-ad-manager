# Phase 1 Acceptance Evidence

Every one of the 13 acceptance criteria from the brief, with the command that
proves it and the observed output. Nothing here is asserted from memory: the
table below is generated by `scripts/acceptance.py`, which talks HTTP to a live
server, spawns fresh processes to prove persistence, and writes
`docs/acceptance-run.json` as machine-readable evidence.

## How to reproduce

```bash
# 0. install
python3 -m venv .venv && .venv/bin/pip install -r backend/requirements.txt
cd frontend && npm install && npm run build && cd ..

# 1. configuration (see .env.example for the full list)
export DATABASE_URL="sqlite+aiosqlite:///./.data/acceptance.db"
export JWT_SECRET="dev-only-jwt-secret-please-rotate-32chars"
export BOOTSTRAP_FOUNDER_EMAIL="founder@crusor.ai"
export BOOTSTRAP_FOUNDER_PASSWORD="crusor-dev-password-1"

# 2. migrate a fresh database
cd backend && ../.venv/bin/alembic upgrade head

# 3. serve the API (an empty users table bootstraps the founder on first boot)
../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 &

# 4. prove all 13 criteria
cd .. && .venv/bin/python scripts/acceptance.py --base-url http://127.0.0.1:8000
```

Exit code `0` means every criterion passed. `SKIP_PYTEST=1` skips only the
slowest check (the full pytest run) while iterating.

### 4. Brand profile create + retrieve — PASS

Retrieval is re-read through `GET /brand/{id}` and the tagline is asserted. The

### 5. Director initialises a stateful workflow — PASS

```
15 nodes, interrupt at human_approval; workflow wf_ef87cbbd7f6e44ec
produced 3 drafts in 8 iterations and is awaiting approval
```

The graph is a supervisor/worker topology, not a sequential chain:

```
START -> intake -> planner -> dispatch
dispatch ->> research_agent | strategy_agent | content_agent
            | creative_agent | growth_analyst_agent | review | fail
<agent>  -> dispatch            (fan-back to the supervisor)
review -> ensure_campaign -> persist_drafts -> request_approval
request_approval -> human_approval  (LangGraph interrupt)
human_approval -> finalize -> END
```

`GET /director/topology` publishes this graph (edges containing a `|` denote
conditional fan-out; `interrupts == ["human_approval"]`). Publishing is not a
node: the graph can plan, create and request approval, and that is where it
stops. The workflow above suspended with `awaiting_human: true` and a populated
`approval_request`.

### 6. Agents invocable via structured interfaces — PASS

```
6 agents expose limits + responsibilities; research run -> succeeded
(run d0780c78…, 3 trace events)
```

`GET /agents` returns, for each of Research, Strategy, Content, Creative, Brand
Guardian and Growth Analyst: responsibilities, declared input/output schemas,
and enforced limits (max attempts, timeout, token budget). `POST
/agents/{name}/run` returns a structured `output` dict — the harness asserts it
is a dict, not free text — together with a `run_id` and trace events
(`run_opened`, `attempt_started`, `run_finished`).

With no LLM provider configured, every agent reports
`generation_mode: "deterministic"` and `requires_human_review: true`. That is
labelled, not hidden.

### 7. Workflow state persists across restarts — PASS

```
a fresh process reconstructed thread wf_ef87cbbd7f6e44ec:
23 checkpoints, identical plan and content ids
```

The harness reads the thread through the API, then spawns a **separate Python
process** with a brand-new `WorkflowRuntime()` and compares checkpoint count,
iteration, the full task plan length and the content id list. They match
exactly, which is only possible if state lives in the database checkpointer.

### 8. Content create + version history — PASS

```
content f10fe4c8… now at v2 with distinct content hashes
```

Versions are immutable rows with a content hash; `GET /content/{id}/versions`
returned both, with different hashes. Creating a version never mutates its
predecessor.

### 9. Approval state machine correct — PASS

```
DRAFT->APPROVED refused (409); submit->approve accepted; editing an approved
item returned it to DRAFT with the approval ledger marked invalidated
```

Verified behaviours:

* illegal transitions are refused with `409 invalid_state_transition`, not
  silently coerced;
* the state space is total over `ContentStatus` — every pair is either allowed or
  explicitly rejected;
* editing approved content creates version N+1, returns the item to `DRAFT` and
  stamps `invalidated_at` / `invalidated_reason` on the approval row;
* replacing a creative asset that carries a live approval does the same;
* repeated `approve` is a no-op returning 200 — it does not append a duplicate
  `approval_records` row.

### 10. Unapproved publication is blocked — PASS

```
DRAFT publish -> 409 approval_required, no publication row;
approved publish -> 503 integration_unavailable, item remains APPROVED
```

This is the criterion the brief called out as critical. Two independent
guarantees:

1. **No approval → no publish.** `POST /content/{id}/publish` on a `DRAFT`
   returns `409 approval_required`, the item stays `DRAFT`, and
   `GET /content/{id}/publications` is still empty — no `published_posts` row was
   invented.
2. **Approval is not enough either.** An `APPROVED` item is refused with
   `publishing_disabled`/`integration_unavailable` because Phase 1 ships no
   network transport. The system does not simulate a successful post.

The publish gate runs in a fixed order inside one transaction: valid approval
(hash-matched to the current version) → connected account → adapter transport.
`test_publish_blocked.py` attempts six distinct bypasses, including approval of a
stale version hash and an item-scoped asset swap.

### 11. Model usage recordable — PASS

```
usage ledger 0 -> 1600 tokens, $0.0000 -> $0.0042 across 1 provider row(s)
```

A usage row was written through `UsageService` and immediately visible at
`GET /usage/summary`: totals moved, cost is non-zero, and the row is attributed
to a provider/model pair. `model_usage` is unique on `(agent_run_id, attempt)` so
retries cannot double-bill. With no provider configured the endpoint honestly
returns `has_data: false` plus a message rather than inventing spend.

## What Phase 1 deliberately does not do

These are absences by design, reported as such in the UI and in
`/system/status` — not gaps to be discovered later:

| Capability | State | Why |
| --- | --- | --- |
| Publishing to any network | `unavailable` | Phase 2. No transport ships; approval and scheduling are complete. |
| LLM inference | `unavailable` | No provider key. Agents run deterministic paths and say so. |
| Image/video generation | `unavailable` | Creative Agent emits an executable art-direction brief; a human uploads bytes. |
| Analytics collection | `no data` (`data_source: "none"`) | Needs platform connectors and published posts. Nothing is estimated. |
| Redis / Celery | `inline` dispatcher | Broker absent in dev; the interface and Celery adapter exist. |
| S3 storage | `local` (degraded) | Filesystem backend for dev; S3 implementation present, unconfigured. |
| pgvector | Python cosine fallback | Extension unavailable on SQLite; dialect-guarded DDL is ready for Postgres. |

## Residual risks carried into Phase 2

Full register in `docs/03-RISKS-AND-DEPENDENCIES.md`. The ones that matter for
sign-off:

* **R1** — PostgreSQL/pgvector behaviour is verified only by offline DDL
  generation here; a real Postgres run is required before production.
* **R14** — SQLite has no `SELECT … FOR UPDATE`; the publish path falls back to
  an optimistic conditional update, which is correct on both dialects but only
  concurrency-tested on SQLite.
* **R11** — the rate limiter is in-process unless `REDIS_URL` is set, so limits
  are per-replica until then.

### The CI dependency defect (diagnosed from a real log, not guessed)

The broker job had been failing with exit 2 in under a second and no reachable
log. A `if: failure()` step now posts the worker log as a commit comment; it
reported:

```text
celery/kombu/redis: 5.4.0 5.7.0 5.0.8
Unrecoverable error: VersionMismatch(
  'Redis transport requires redis-py versions 6.1.0 or later. You have 5.0.8')
```

Celery 5.4.0 accepts any `kombu<6`, so an unpinned install resolves kombu 5.7,
whose Redis transport requires redis-py ≥ 6.1. `requirements.txt` now pins
`kombu==5.6.2` (declares `redis>=4.5.2,<6.5`) together with `redis==5.0.8`, a pair
verified locally by a real worker round-trip. The job also gained a `pip check` +
resolved-versions step, a redis-py readiness probe, a worker step that fails when
the worker never reports ready, and a unique worker node name.
